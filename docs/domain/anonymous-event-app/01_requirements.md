# 匿名イベントアプリ — 要件定義

## 受け取った要求

> **「職場の人を気軽に誘えるアプリを作りたい。ランチに誘うのは意外とハードルが高いから、誘いやすく、断りやすくしたい。**
> **匿名で『今日ランチに行きたい。4人集まったら行く』という募集をかけられて、参加がその人数に達したら実施が決まる。誰が言い出したかも、誰が押したかも、成立するまで見えない。集まらなくても誰も傷つかない。**
> **成立したら誰が行くかはみんなに見えて、そこで『ここがいいかも』と店の提案が来る。決まらなければ会社の周りの店リストも見たい。店の情報は Google マップから出してほしい。**
> **行った店には星と一言のレビューを書けるようにして、行き先の選択肢をどんどん増やしたい。レビューは名前が出る。知らない誰かの点数より、一緒に働いている人の『ここ好き』のほうが信用できる。**
> **ランチに限らず、飲み会・スマブラ大会・日付を指定したランニングまで、『2時に行く人〜』くらいの軽さで使いたい。**
> **入口は Slack に流れる URL と、ホーム画面のアイコン。Slack への投稿で立案者がわかってしまわないように。**
> **使うのは、まずは自分の会社ひとつ。」**

## 確認したいこと（質問リスト）

### 匿名と開示

| 質問 | 回答（すべて確定済み） |
|---|---|
| 成立したら参加者の名前は誰に見えるか | **成立したら全体に公開**（誰が行くかを全員が見られる）。終了後も**当日中は「終了」として一覧に残り**、翌日からは参加者の履歴にだけ残る |
| 立案者が誰かは開示されるか | **されない。立案者はずっと匿名**。開示後も参加者の一人としてフラットに表示され、「誰が言い出したか」は永遠に出ない。成立後にイベントが取り消された場合も「誰が取り消したか」は出さない |
| 「断る」という操作はあるか | **作らない**。参加を押さないことが断り。不参加という記録は **DB に行として残らない**。ただし「詳細を開いた」ことはアクセスログには残るので、主張の範囲は DB に限る（ログの扱いは次の行） |
| 不成立のイベントの記録はどうなるか | **本人の履歴にだけ残る**。「自分が立てたもの」「参加を押したもの」の両方が、成立・不成立・取り消しを問わず自分の履歴に残る。他人には最初から最後まで見えない |
| 不成立を Slack に流すか | **流さない。静かに消える**。イベント時の投稿はそのまま（アプリを開けば終了していることはわかる）。「誰も傷つかない」を最優先 |
| イベントの URL を直接踏んだら何が見えるか | 状態と閲覧者で決まる。**募集中・成立・終了当日は誰でも詳細まで見える**（成立後は名前も＝全体公開どおり）。**終了の翌日以降・不成立・取り消しは最小表示のみ**——一律「このイベントは終了しました」の一文だけを返し、タイトル・人数・名前も、不成立か取り消しかの区別も出さない（区別を出すと「誰かの誘いが流れた」が可視化される）。Slack に URL が残り続けても翌日以降に何も漏れない。**組み合わせは下の一覧表に全部書き出す**（文章で列挙すると抜ける） |
| 開示された名簿から名前が消えることはあるか | **ある。そして見える**。成立後の取り消しは集合日時まで可で、名簿は都度計算（＝いま行く人）なので、公開済みの名簿から名前が消えるのを他の参加者は見られる。「不参加の記録は存在しない」が通るのは開示前まで、と範囲を切る（名簿を成立時点で固定すれば隠せるが、名簿にいる人が来ない状態が生まれるので採らない）。**参加を押す前にこのことを伝える** |
| 匿名が守られる範囲はどこまでか | **アプリの表示境界とログまで**。参加・立案・詳細の各エンドポイントは会員識別子とセッショントークンをログに出さない（出すならハッシュ化した相関 ID のみ）／リクエストボディはログしない／例外通知に会員 ID を含めない。そのうえで **DB 権限を持つ人に対して匿名は成立しない**——隠せないので限界として明記する |
| 開示する名簿の並び順は | **表示名の五十音順**。参加順・作成時刻・ID と相関する並び（先頭＝立案者になる並び）を禁止する。立案者の特定を防ぐ。並べるために**表示名の読み（カナ）を登録時に必須で受け取る**——漢字の表示名だけでは読み順に並べられない |
| 参加人数の途中経過は見えてよいか | **人数の進捗だけ見せる**（「いま 2/4」）。イベント一覧でも詳細でも表示する（あと一人で成立、が見えて参加の背中を押す）。誰が押したかは見せない。**分数を出すのは募集中だけで、成立後は実数だけを出す**（「行く人 5 人」）——あと乗りの「5/4」や取り消し後の「3/4 なのに成立」は壊れて見え、成立を取り消さないという要件そのものが疑われる |

**状態と閲覧者ごとの見え方**（上の 3 行を組み合わせた結果。認可のテストはこの表と突き合わせる）

| 状態 | 未ログイン／それ以外の会員 | 立案者本人 | 参加者 |
|---|---|---|---|
| 募集中 | 一覧に出る。詳細（タイトル・集合日時・締切・進捗 2/4）まで見える。名前は誰も出ない | 同じ＋「自分が立てた」印 | 同じ＋「参加中」印 |
| 成立 | 一覧に出る。詳細＋名簿（表示名・行く人 N 人・提案 3 件）。立案者の区別は無い | 同じ＋自分向けの印 | 同じ＋自分向けの印 |
| 終了（当日） | 一覧の末尾に「終了」として出る。中身は成立と同じ | 同じ | 同じ |
| 終了（翌日以降） | 最小表示の一文だけ。一覧に出ない | 履歴から詳細（名簿込み）を開ける | 履歴から詳細（名簿込み）を開ける |
| 不成立 | 最小表示の一文だけ。一覧に出ない | 履歴に残る（詳細を開ける） | 押した人の履歴に残る |
| 取り消し | 最小表示の一文だけ。一覧に出ない | 履歴に残る | 押した人の履歴に残る。成立後の取り消しは名簿も見えたまま残る |

立案者だと分かる情報は、どの状態でも本人以外には出ない（「自分が立てた」印は本人の画面だけ）。最小表示の画面には「ログインすると、参加していたイベントは履歴で見られます」の 1 行を置く——状態を漏らさないので上の判断は変わらない。

### 成立のルール

| 質問 | 回答（すべて確定済み） |
|---|---|
| 「4人集まったら」に立案者は含むか | **含む**。立案者込みの合計人数で数える |
| 締切はどう決まるか | **立案者がイベント時に設定。既定は集合日時**。届かなければその時点で不成立。設定できる範囲は**現在より後、かつ集合日時以前**（下限が無いと「昨日締切・明日集合」の参加できないイベントが作れてしまう）。代償として、数日先のイベントは既定のままだと直前まで人数が固まらない——店の予約が要るときは立案者が締切を手前に設定する |
| 成立後の取り消し・あと乗り | **両方 OK**。取り消しでしきい値を下回っても成立は取り消さない（行くかどうかは当日の人たちに任せる）。できるのはどちらも集合日時まで |
| 締切は集合日時より後にできるか | **できない**。締切 ≦ 集合日時。「始まってから成立する」という状態を作らない |
| 成立はいつ判定されるか | **参加が登録されたその場で即時に判定・開示する**（バッチではない）。バッチが動かすのは締切（不成立）と集合日時（終了）と期限切れセッションの掃除だけ。判定が重なったときは成立を優先 |
| 参加できるかは何で決まるか | **状態と現在時刻の両方**で決まる（状態だけを見ると、バッチが動く前の数十秒に締切後の参加を受け付けてしまう）。募集中は締切まで、成立後は集合日時まで。**「ちょうどその時刻」は締まっている**（12 時締切なら 12 時 00 分は不可）——バッチ側の条件と裏表になり、隙間も重複も出ない |
| 成立が二重に起きないか | **起きない**。同時に最後の 2 人が押しても、成立にする更新は「まだ募集中である」ことを条件に付けるので成功するのは 1 つだけ。Slack への通知はその更新が成功したときだけ出す（成立後に人数が再び達しても何も起きない） |
| 「開催が終わった」はいつか | **集合日時を過ぎたら終了**（終了時刻・所要時間の概念は持たない。あと乗り・取り消しもここまで）。ただし表示は**当日中は「終了」ラベル付きで一覧に残す**——集合直後に「誰が来るんだっけ」を一覧からすぐ開けるように。翌日からは参加者それぞれの履歴にだけ残る |
| 成立人数の下限は | **2 人以上（立案者込み）**、上限は 50 人。1 人ではイベントの意味がない。2 人で成立した場合、名簿のもう 1 人から見れば立案者は確定するが**許容する**——立案者は元から必ず名簿に載る（特定確率は 1/n）ので 2 はその端にあたるだけで、匿名が本当に守るべき不成立時は何も出さない。「一人来てくれれば行くランチ」は要求の中心なので下限を上げない（→ 03 付録B 論点8） |
| 公開後のイベントは編集できるか | **できない**。間違えたら取り消して立て直す。「参加したあとに条件が変わる」問題がそもそも起きない。ただし立て直しが積み上がらないよう、①**公開前に確認画面を 1 枚置く**（Slack へ投稿する前に止める）②**参加が 0 件のあいだの取り消しは Slack に流さない**（誰も迷わないため。「取り消し → すぐ立て直し」の 2 投稿が並ぶと同一人物のものと分かり、立案者が絞られるのも同時に防げる） |
| 立案者は自分の参加だけ取り消せるか | **募集中は取り消せない**（消せると立案者不在の匿名イベントが募集を続けてしまう）。**成立後は他の参加者と同じに取り消せる**——募集が終わっていて名簿も開示済みなので、禁止の理由が効かない。副産物として「毎朝同じイベントを立てる人は必ず名簿に載る」がなくなり、名簿を何日も重ねて立案者を絞る観測が成立しなくなる |
| 定員（上限人数）はあるか | **持たない**。あと乗り自由と整合させ、今回は作らない→ 03 付録A（今回やらないこと）に載せる |
| 立案者はイベントをやめられるか | **「イベントの取り消し」として扱う**（集合日時まで。終了・不成立のあとは不可）。専用の「取り下げ」概念は作らない。**取り消しは成立前・成立後を問わず bot が Slack に知らせる**（誰が取り消したかは出さない）——URL は Slack に流れたままなので、黙って消すと参加しようと押した人が迷う。アプリ内では、成立前の取り消しは本人の履歴にだけ残り、成立後の取り消しは参加者にも見える |

### 利用範囲と規模

| 質問 | 回答（すべて確定済み） |
|---|---|
| 誰までがイベントを見られるか。将来の規模は | **1社で使う。閲覧は URL を知っている人なら誰でも**——Slack に流れた URL を開けば、ログインなしでイベントの一覧・詳細・店リスト・レビューまで見られる。**参加・立案・レビュー投稿はログイン必須**（本人の履歴を残すため）。グループ分け・マルチテナントは今回やらない |
| 会員登録は誰でもできるか | **既存のメール＋パスワード登録をそのまま使い、今回は制限を作らない**。根拠は「URL が出るのは社内 Slack だけで、混入が起きたら DB 直接対応で止める」——閲覧を URL で開いている以上「URL を知っている人しか来ない」は根拠にならない（社外の第三者が会員になり、匿名でイベントを立てて bot に社内へ投稿させられる）。メールドメインの前方一致チェック 1 箇所で塞げるので、費用対効果の比較として 03 付録A に残す |
| 会社の座標・bot などの設定は誰が管理するか | **設定ファイル（エンジニア作業）で済ませる**。管理画面・管理者ロールは今回作らない。「変更頻度がほぼゼロ」が当てはまるのは**座標だけ**で、bot トークンには失効・ローテーション・再インストールがある。座標などの非機密は設定ファイル（git 管理）、**bot トークンは環境変数（git の外）**に分け、起動時に座標の妥当性とトークンの疎通を検証して不正なら起動失敗 |
| DB 直接対応は具体的にどうやるか | 接続は踏み台経由の read-only を既定とし、更新は別ロール。**実施は 2 人**（実行者と確認者）。実行前に対象を SELECT で確認し、実行した SQL と件数を記録する。`DELETE` ではなく `state` の更新を第一手段にする（`Member.Status` はこの運用の受け皿） |
| 苦情・問い合わせは誰が受けるか | **オーナー部署と一次受け（Slack チャンネル）と、研修が終わったあとの引き継ぎ先を決めておく**。機能は作らない（通報・管理画面なし）が、社内に出せば苦情は必ず人に来るため、受け手が空席のままにはしない |
| 費用の上限は誰が見るか | **月額上限と、上限に達したときに止める人を決める**。閲覧はログイン不要で店リストは表示のたびに Google を呼ぶので、URL が社外に出れば誰でも課金を発生させられる。GCP 側で予算アラートと 1 日あたりのクォータ上限を設定し、通知先を書く。Google 呼び出しは 2 秒でタイムアウト、連続 N 回の失敗でフォールバックへ倒す（Google のエラーは成功レスポンス中の状態値で返るため、例外処理だけでは拾えない） |
| バックアップと復旧はどうするか | 頻度・保持期間・どこまで戻せるかを決める。**復旧には副作用がある**——参加の取り消しは物理削除なので、過去時点へ戻すと取り消した人の参加行が復活し、成立していれば開示名簿にその人の名前が出る。復旧手順に是正を含める |
| 時刻の基準は何か | **保存・比較はすべて JST 固定、日付境界は JST の 00:00**（「当日中は一覧に残す」の当日もこれ）。JVM・DB・コンテナのタイムゾーンを起動時に検証し、不一致なら起動失敗。フロントは日付境界を判定せず、サーバが出した表示ラベルを受け取る |
| 公開ページのキャッシュはどうするか | イベントの一覧・詳細は `private, no-store`（少なくとも `no-cache` ＋ `Vary: Cookie`）。同じ URL の中身が状態と閲覧者で変わるため、中間キャッシュに成立後の名簿や最小表示が残らないようにする |
| 不適切なレビュー・イベントへの対処は | **今回は作らない**。本人が自分のものを消せるだけ。通報・強制削除の仕組みは作らず、問題が起きたら DB 直接対応 |

### 店とレビュー

| 質問 | 回答（すべて確定済み） |
|---|---|
| 店は誰がどう登録するか | **基本は外部 API（Google Places）の検索結果から選ぶ**。API に無い店・社食・オフィス内の場所は手動でも登録できる。店のレコードは最初にレビューが書かれるときに作る——Google の検索結果を選ぶと店名がフォームに転記され、**会員が確定した呼び名**として保存する（共有マスタなので誰でも直せる） |
| 同じ店が二重に登録されるのを防げるか | **手動登録の前に、既存の店を名前の前方一致で出して「これですか？」と選ばせる**。DB 側は Google の店を指していない行の店名に一意制約をかけて最低限だけ止める（「社食」「3F社食」のような表記揺れは止まらない、と割り切る）。重複した店をあとから 1 つにまとめる操作は今回作らない（→ 03 付録A） |
| 店名を誰かが上書きしたらどうなるか | **共有マスタなので誰でも直せる**が、更新時に手元の更新日時を突き合わせて、他の人が先に直していたら弾く（409 を返して読み直させる）。変更前の値は残さないので、**`place.name` はこのアプリで唯一「DB 直接対応でも復旧できないデータ」**になる（→ 03 付録B） |
| 「周辺の店リスト」とは何か | **会社の座標（設定として1つ登録）を基準に Google Places で周辺検索した結果**＋登録済みの店とそのレビュー。会員個人の位置情報は使わない |
| Google Places の課金・規約 | 従量課金（社内規模なら無料枠内の想定）。**規約上、店名等のキャッシュに期限がある**ため、無期限に保存してよいのは place_id。レビュー表示用に店名をどう持つかは詳細設計の論点にする→ 03 付録B（判断の記録）で扱う |
| レビューの多重度・形 | **行くたびに書ける**（1人1店に複数可）。項目は**星（5段階）と一言だけ**。「何時頃に行って並んだか」は一言の中に自由に書く（構造化しない）。自分のレビューは編集・削除可——**そこへ行く導線として履歴に「自分のレビュー」を 1 タブ足す**（半年で同じ店に 50 件並ぶ人が、他人のレビューに混ざった自分の分をスクロールで探さずに済む）。同じ店に自分の直近レビューがあるときは「前回のを直す／新しく書く」を聞く |
| 「ここがいいかも」の提案はどう出るか | **アプリが自動で出す**。成立したイベントの詳細画面に**常に 3 件表示する**（成立の瞬間に送りつけるものではない。保存もせず表示のたびに計算する）。並べ方は**縮小平均**——`(3 × 全店の平均星 + その店の星の合計) ÷ (3 + その店のレビュー件数)` の高い順。単純平均だと星 5 が 1 件だけの店が常に 1 位になり、件数の下限で切ると新しい店が永久に出てこない（「行き先の選択肢を増やしたい」と逆を向く）。同点はレビュー件数の多い順、それも同じならレビューが新しい順。3 件に届かない分は「登録済みだがレビューがまだ無い店」で埋め、なお足りなければ Google（会社周辺・評価順）で補う。**参加者からの手動提案は作らない** |
| 立案時に店を選べるか | **選べない（今回やらない）**。場所を伝えたいときはタイトルに書く（「今日ランチ@サイゼ」）。イベントは店への参照を持たない |
| 店の「決定」という操作はあるか | **作らない**。アプリは提案とレビューを見せるだけで、どこに行くかは会話で決める。行き先はイベントに記録されない |
| レビューはイベントに紐づくか | **紐づけない**。イベントを経由しなくても書ける。「食べたらそのまま書ける」は画面の導線の話とする |
| 実名レビューから匿名参加が推測される問題 | **許容する**。成立時点で参加者は全体公開されるので、実質的な追加リスクは小さい |

### 入口・通知

| 質問 | 回答（すべて確定済み） |
|---|---|
| Slack へは誰が投稿するか | **bot が自動投稿**。立案者は一切露出しない。**投稿先チャンネルは立案時に選べる**（bot が入っているチャンネルの中から） |
| 成立・不成立の通知はどこへ | **成立したときと、取り消されたとき（成立前後を問わず）に bot が Slack に投稿**（人数のみ。名前は出さない）。**不成立だけは何も流さない**（締切で自然に終わるため。「誰かの誘いが流れた」を可視化しない）。名前の開示はアプリ内で見る |
| bot の投稿に失敗したら | **その場で 3 回まで再試行し、それでも駄目なら諦めてログに残す**（あとから投げ直す仕組みは作らない）。**失敗してもイベントは公開のまま**（アプリ内では見える）。立案者が気づけるよう、**作成完了画面に「Slack への投稿に失敗しました。URL をコピーして共有できます」の 1 行を出す**。投稿の記録が無いまま成立・取り消しが起きたときは、スレッド追記ではなく新規投稿として流す |
| アプリの形態 | **インストール不要の Web アプリ**。URL を開けばそのまま使える。スマートフォンのホーム画面にショートカット（ホーム画面に追加）を置けて、企画の一覧や店リストを見たいときにいつでも開ける |
| 自分の参加を自分に見せるか | **見せる**。一覧の各行に本人向けの印（参加中／成立した）を出し、履歴への入口を一覧と同じ階層に置く。本人に自分の参加を見せることは匿名性を何も損なわず、「押したか思い出せないイベントを押して二重参加のエラーになる」も同時に消える。個人向けのプッシュ通知は今回作らない（→ 03 付録A） |
| 毎日立てる人の手間を減らすか | **減らす**。「前回と同じ内容で立てる」（直近の自分のイベントを初期値にする）を用意し、成立人数の既定は 4 人、投稿先チャンネルの既定は前回選んだもの、締切の既定は集合日時にする。**既定値は実装者の裁量ではなく仕様**なので要件に書く |
| 匿名の範囲を利用者にどう伝えるか | **説明ページは作らず、画面に 2 行入れる**——イベント作成画面と参加ボタンの付近に「匿名なのは成立するまで」「成立すると参加者全員の名前が出る（立案者もその中にいる）」。初回ログイン時にも一度出す。文言は上の質問リストからそのまま引く（新しく決めることは無い） |
| 一覧の並び順は | **集合日時の昇順**（近いものが上）。終了当日のイベントは末尾に置く。「あと一人で成立」が目に入る順にする——進捗を公開する理由と揃える |

### 参加しない人に見えるもの

「誰も傷つかない」を立案者と参加者だけで考えると抜ける視点。**進捗・名簿・bot 投稿の 3 点をここで横断して 1 回判断する。**

| 質問 | 回答（すべて確定済み） |
|---|---|
| 「断りやすい」とは何を満たすことか | **2 つに分けて、片方だけを満たすと決める**。①**記録が残らない**——不参加は DB に行として残らない（徹底して満たす）②**押さないことが目立たない**——これは**満たしていない**。進捗も名簿も公開なので、母集団が小さい場では「押していないのは自分だけ」が本人にも周囲にも計算できる。代償として明記する |
| 押していない人に進捗が見えることは | **許容する**。進捗の公開は「あと一人で成立、が見えて参加の背中を押す」ためで、要求の中心にある。押される側の圧はその裏返しとして受け入れる |
| 進捗の変化を定点観測されることは | **許容する**。11:34 に 1/4、11:36 に 2/4 を見た人は「その 2 分の間に誰かが押した」ことを知る（自分の分は差し引ける）。粗い段階表示（「あと 1 人」）にすれば防げるが、背中を押す価値を削るので採らない |
| 不成立で一覧から消えるのを定点観測されることは | **許容する**。昨日 1/4 だったイベントが今日消えていれば「誰かの誘いが誰にも乗られなかった」を目撃できる。不成立も当日中は一覧に残せば消滅の観測点そのものが消えるが、不成立と終了を一覧で同じに見せる複雑さを今回は持たない |
| 名簿に名前が無いことで「行っていない」が分かることは | **許容する**。不参加は記録されないが、成立名簿の公開が同じ働きをする。機能では閉じられない |
| 投稿先チャンネルを選べることは | **許容する**。外したい人がいないチャンネルに投稿すれば、全社に開かれた建前のまま実質の招待制になり、成立名簿は全体公開なので呼ばれなかった人には見える。投稿先を設定ファイルで 1 チャンネルに固定すれば閉じるが、立案の自由を残す |
| bot の投稿が流れ続けることは | **許容する**。1 件につき公開・成立・取り消しで最大 3 投稿。ミュートや通知オフは Slack 側の機能に任せる（アプリでは持たない） |
| タイトルに他人の名前を書かれたら | **「タイトルに他人の個人名を書かない」をルールとして明記する**。立案者は永久に匿名で通報も無いので、書かれた人は書いた人を特定できない。困ったときの窓口は苦情の一次受け（Slack チャンネル）とし、対応は DB 直接対応で消す |
| 誘いを見ずに店情報だけ使えるか | **使える**。店リストへはイベント一覧を通らずに開ける導線を置く（ランチ情報を得るたびに募集の進捗と成立名簿を必ず通る、という形にしない） |

## 業務フロー

```
[運営者（管理者）]
 0. 会社の座標・Slack bot を設定する（設定ファイル。画面は作らない・初回のみ。投稿先チャンネルは立案時に bot 参加チャンネルから選ぶ）

[立案者（匿名）]
 1. ログインし、イベントを立てて公開する（内容・集合日時・成立人数（自分込み・2〜50人・既定4）・締切（既定＝集合日時。現在より後で集合日時以前）・投稿先チャンネル（既定＝前回選んだもの）。場所を伝えたいときはタイトルに書く）。**投稿する前に確認画面で1回止まる**。公開した時点で、自分が参加の1人目になる
 2. 間違えたときは取り消して、立て直す（公開後の編集はできない。「前回と同じ内容で立てる」で入力を引き継げる）
 3. やめたくなったら、集合日時までイベントを取り消せる（終了・不成立のあとは取り消せない）

[bot（Slack・外部）]
 4. 公開されたら、選ばれたチャンネルへ URL を投稿する（立案者の名前はどこにも出ない）。投稿の記録（channel / message の ID）をイベント側に写す。3回試して駄目なら諦め、立案者の画面に失敗を出す
 5. 成立したときだけ、元の投稿につなげて結果を流す（人数のみ）
 6. 取り消されたときは（成立前・成立後を問わず）「このイベントは取り消されました」を流す（誰が取り消したかは出さない）。ただし**参加が0件のあいだの取り消しは流さない**（誰も迷わないため）

[参加したい人]
 7. Slack の URL かホーム画面のショートカットから開き、イベントの一覧・詳細を見る（ここまでログイン不要。集合日時が近い順に並び、進捗「いま 2/4」が見える）
 8. 「参加」を押す（ここでログイン。誰が押したかは成立まで誰にも見えない）。未ログインで押した場合はログイン後に詳細へ戻り、もう一度押してもらう（気づかないうちに参加していることが起きないように）
 9. 気が変わったら取り消す。もう一度参加してもよい（どちらも集合日時まで。立案者が自分の参加だけを取り消せるのは成立後）

[システム]
10. 参加が登録されたその場で人数を判定し、成立人数に達したら即時に成立・名前の開示を行う（「まだ募集中である」ことを条件にした更新なので、同時に押されても成立は1回だけ。誰が立案者かは出さない。名簿は表示名の五十音順）
11. 【バッチ】締切を過ぎても達していなければ、不成立にする（判定が重なったときは成立を優先。記録は各自の履歴のみ）
12. 【バッチ】集合日時を過ぎたら、終了にする（当日中は「終了」として一覧に残り、翌日からは参加者それぞれの履歴だけに残る）。あわせて期限切れのログインセッションの行を消す

[参加者（成立後）]
13. 成立したイベントの詳細画面に常に出ている店の提案（3 件）を見る（「決定」の操作はなく、行き先は会話で決める。アプリは行き先を記録しない）
14. 決まらなければ、会社周辺の店リスト（Google Places の検索結果＋みんなのレビュー）を見る。API に無い店・社食は、最初のレビューを書くときに手で登録する
15. あと乗りする人・取り消す人が出てもよい（集合日時まで。人数を下回っても成立のまま）
16. 行ったあと、店に星（5段階）と一言を実名でレビューする（何時頃に行って並んだかは一言の中に書く）。自分のレビューはあとから直せる・消せる（履歴の「自分のレビュー」から開く）

[Google Places（外部）]
17. 店リストが開かれたら、会社の座標の周辺の店を検索して返す

[例外・ルール]
 - 誰が立てたか・誰が参加を押したかは、成立するまで誰にも見えない。立案者は成立後も一切出ない
 - 開示する名簿は表示名の五十音順（表示名の読みで並べる。参加順・作成時刻と相関する並びにしない）
 - 現在 < 締切 ≦ 集合日時。過去の集合日時ではイベントを立てられない。公開後の編集はできない（取り消して立て直す）
 - 参加できるかは状態と現在時刻の両方で決まる。募集中は締切まで、成立後は集合日時まで。その時刻ちょうどは締まっている
 - 成立人数は 2 人以上 50 人以下（立案者込み）。同じイベントに二重参加はできない。取り消してからの再参加は自由。立案者が自分の参加だけを取り消せるのは成立後
 - 成立後に人数を下回っても成立のまま。進捗の分数は募集中だけに出し、成立後は実数だけを出す。終了・不成立のあとにイベントは取り消せない
 - bot の投稿は3回まで再試行して諦める。失敗してもイベントは公開のまま。参加0件のあいだの取り消しは流さない。投稿の記録が無いままの成立・取り消しの通知は新規投稿で流す
 - 時刻はすべて JST で保存・比較し、日付の境界は JST の 00:00。会員の識別子とセッショントークンはログに出さない
 - 閲覧はログイン不要、書き込み（参加・立案・レビュー投稿）はログイン必須。通知・見え方・Google 不通時・URL 直接アクセスの詳細は質問リストの該当行に一元化する
```
