### 6 類型の確認

| 類型 | いる／いない | 理由 |
|---|---|---|
| 運営者・本部 | **いる（ただし画面なし）** | 会社の座標・Slack bot・チャンネルの設定を持つが、設定ファイル（エンジニア作業）で済ませると確定。管理者ロール・管理画面は作らない → **モデルには現れない** |
| 承認者・監査 | いない | 承認フローなし。「軽さ」が価値なので作らない |
| CS・サポート | いない（確定） | 不適切投稿への対処は今回作らない。本人が自分のものを消せるだけ |
| 経営・分析 | いない | 集計要求なし。ただし「何を消してよいか」の判断（保存期間）には関わる → 前提へ |
| バッチ・スケジューラ | **いる** | 「締切で不成立」「集合時刻で終了」は誰の操作でもなく時間で起きる。状態遷移の逆引きテストで発見 |
| 外部サービス | **いる** | Slack（bot 投稿）と Google Places（店舗検索）。どちらも所持物なし。相手側 ID と結果を写すだけ |

### 段階1の採否（確定・2026-08-20）

- **人間のアクターは「社員」1本**。立案者・参加者はアクターではなく役割（権限の違い＝取り消しは立案者だけ、として表す）
- **イベントは共有の場のもの、参加は各自のもの、店は共有マスタ**
- 帰結: 教材の「アクターの利用範囲＝コンテキスト境界」をそのまま当てるとコンテキストは 1 つになるが、担当者軸が無効（人間が社員 1 種）のため残り 2 軸で判断 → 下の「コンテキストの判断」で **3 つに確定**

### 網羅スイープの結果（プロンプトA実行・2026-08-20 16:56）

手順書のプロンプトA（新規用）を確定済み要求文に対して実行。段階1の結論と突き合わせて、**新発見は 1 つ**。

- **Slack 投稿の記録（channel / message の ID）**: bot が募集を投稿したときの相手側 ID をイベント側に写しておかないと、成立時に同じ投稿へ結果をつなげられず、再投稿の重複も防げない。教材の `Payment.transactionId` と同型（外部の相手側 ID を写す列）。**段階 4〜5 のふるい分け対象に追加する**
- 大規模（B）で増える所持物（テナント / グループ / 管理者ロール / 通報・強制削除 / 登録制限）は「作らない」ではなく**判断が変わる条件**として記録: 複数社展開が決まったら全モデルに境界の鍵が要る（前提の「規模によって変わりそうなモデル」と同じ）

## 業務フローの棚卸し（段階3・1周目）

番号を振らない・振り分けない・行頭に主語。分からないことは質問リストへ。

```
- [運営者]   会社の座標・Slack bot・投稿先チャンネル候補を設定する（設定ファイル）

- [立案者]   ログインして募集を作る（内容・集合日時・成立人数・締切(既定=集合時刻)・店(任意)・投稿先チャンネル）
- [立案者]   公開する（＝自分が参加1人目として数えられる）
- [立案者]   締切前に募集を取り消す
- [立案者]   成立後に募集を取り消す
- [立案者]   自分の履歴で、立てた募集（成立・不成立・取り消し込み）を見る

- [社員]     Slack の URL かホーム画面ショートカットから開く（ログイン不要で閲覧）
- [社員]     募集一覧を見る（進捗 2/4 が見える）／募集の詳細を見る
- [社員]     参加を押す（ここでログイン）
- [社員]     参加を取り消す（集合時刻まで）／取り消したあと、もう一度参加する
- [社員]     成立後、開示された参加者の名前を見る
- [社員]     成立後、店を提案する（実名・参加者のみ）
- [社員]     会社周辺の店リストを見る（Google Places 検索＋登録済みの店とレビュー）
- [社員]     店を手動で登録する（API に無い店・社食）
- [社員]     店に星と一言のレビューを書く／自分のレビューを編集・削除する
- [社員]     自分の履歴（立てた・押した）を見る

- [システム] 参加数が成立人数に達したら、成立にして名前を開示する
- [システム] 締切を過ぎても未達なら、不成立にする
- [システム] 集合時刻を過ぎたら、終了にする（一覧から消えて履歴だけになる）

- [bot]      募集の公開時に、選ばれたチャンネルへ URL を投稿する（立案者を出さない）
- [bot]      投稿の記録（channel / message の ID）をイベント側に写す
- [bot]      成立したときだけ、結果を投稿する（人数のみ）

- [Google]   会社座標の周辺の店を検索して返す／店の詳細（place_id・店名）を返す

- [-]        誰が立てたか・押したかは成立まで見えない（主語なし＝例外行き）
- [-]        立案者は成立後もずっと匿名
- [-]        締切 ≦ 集合時刻
- [-]        成立後に人数を下回っても成立のまま
- [-]        不成立・成立前の取り消しは本人の履歴のみ
- [-]        終了後は参加者の履歴のみ
- [-]        閲覧はログイン不要、書き込みはログイン必須
```

> **追記（2026-08-20 17:14）**: 発注者の指摘で「店の提案」の解釈を訂正。参加者が手動で提案するのではなく、**アプリが成立（開示）のタイミングで自動で提案を出す**（社内レビュー高評価順に 3 件程度・少なければ Google の評価・近さで補完・手動提案は作らない）。棚卸しの `[社員] 成立後、店を提案する` の行は `[システム] 成立時に店の提案を 3 件程度添える` に読み替える。主語が社員からシステムへ移った＝提案は社員の所持物ではなく、成立時にイベントへ添えられる生成物になる。

### 5軸チェックで拾ったもの

| 軸 | 拾ったこと | 扱い |
|---|---|---|
| 数 | 定員なしは確定済み。**成立人数の下限が未定義**（1 だと自分だけで成立してしまう） | → 質問 |
| 数 | 同じ人が同じ募集に2回参加は不可（1人1回）。別の募集への同時参加は制限しない | → 例外・ルールへ |
| 時間 | **過去の集合時刻では募集を立てられない** | → 例外・ルールへ |
| 時間 | **公開後の募集の編集（内容・時刻・人数の変更）ができるか未定義** | → 質問 |
| 打ち消し | 参加取り消し→再参加は可（回数制限なし） | → 例外・ルールへ |
| 打ち消し | **成立後に取り消されたとき、参加者への知らせ方が未定義**（行く気でいる人がいる） | → 質問 |
| 同時 | 4人目が同時に2人来ても、定員がないので両方入って成立するだけ。問題にならない（定員なしの判断がここで効いた） | 対応不要 |
| ゼロ | 参加0のまま締切→不成立（既定どおり）。提案0・レビュー0も問題なし。成立後に全員抜けて0でも成立のまま（確定済み） | 対応不要 |
| 否定形 | **Google Places が使えないとき**、店リストは登録済みの店とレビューだけでも出す（誘いは店なしで回るので致命傷にならない） | → 例外・ルールへ |

担当者軸が使えないので、**変更の理由・ライフサイクル・データの性格**で切った。発注者の当初案（会員・イベント・店）と一致。

| コンテキスト | 変更の理由 | ライフサイクル | データの性格 |
|---|---|---|---|
| **会員**（既存 `edu.customer` をそのまま使う） | 認証方式・セキュリティ | 年単位 | 秘匿（パスワード・セッション） |
| **イベント**（誘い。記号名は段階6で評価して決める） | 誘いのルール（成立・匿名・締切）の改善 | **数時間〜1日で終わる揮発** | 匿名が絡む。終了後は本人履歴のみ |
| **店**（店とレビュー。記号名は段階6で評価して決める） | Google Places 連携・レビュー拡充 | **無期限に蓄積するストック** | 全部実名・全公開 |

- 判断を支える事実: ①会員は既存資産で分離済み ②「レビューはイベントに紐づけない」と決定済み＝店の世界はイベントを知らずに完結 ③参照は ID のみ・一方向（イベント→会員、イベント→店、レビュー→会員・店）で循環なし
- 分けすぎではない: 教材の目安「最初は 3〜5 個」の下限。1 つに畳むと揮発・無期限ストック・認証情報が同居し「何を消してよいか」の線が消える

## 追記（2026-08-20 18:38）: 終了イベントの見え方

「集合時刻で一覧から消える」だと、集合直後に「誰が来るんだっけ・詳細なんだっけ」を確認しようとした人が履歴を探すことになる、という発注者の指摘。**状態の定義（終了＝集合時刻。あと乗り・取り消しもここまで）は変えず、表示だけ「当日中は『終了』ラベル付きで一覧に残す」に変更**。翌日からは参加者の履歴のみ（従来どおり）。検討した代案: 現状維持（履歴から見る）／参加者にだけ残し続ける（人によって見え方が変わり説明が増えるため不採用）。

## 追記（2026-08-20 段階4〜5）: ふるい分けの判断2件

- **イベントの種類（ランチ・飲み会…）は対象外**。要求文の例示にすぎず、カテゴリ絞り込みの要求もない。タイトルで十分。区分値にすると「スマブラは何に入る？」というメンテが生まれる。足りないより増やしすぎの方が直しにくい。
- **店の提案3件は保存せず毎回計算**。教材の「営業中/本日休業を保存するか→しない」と同型。保存すると、揮発データであるイベントに提案だけが残るねじれ（スナップショットは消えない側に置く、の逆）が出る。代償: 表示のたびに提案が入れ替わりうる（最新レビュー反映と裏表）。→ 03 の判断の記録候補。
- ふるい分けの結果: **新規エンティティ4つ（イベント・参加・店・レビュー）＋既存 Customer 系**。動詞の書き込み先4か所と一致。値オブジェクト候補は成立人数（2以上）と星（1〜5）で、型にするかは段階8で決める。対象外15件。

## 追記（2026-08-20 段階5後）: 成立前の取り消しも Slack に流す

発注者の指摘: URL は Slack に流れたままなので、成立前に取り消して黙って消すと、参加しようと URL を押した人が迷う。**取り消しは成立前・成立後を問わず bot が知らせる**（匿名のまま）に変更。不成立は従来どおり流さない——不成立は締切（≦集合時刻）で自然に終わるので「生きてるはずの URL」問題が起きにくく、「誰かの誘いが流れた」の可視化を避ける原則を優先。取り消し＝生きている時間帯に人為的に消える、不成立＝時間切れ、という性質の違いで通知の要否が分かれた。
