## アクター洗い出し

### 7 つの問い

| # | 問い | 答え |
|---|---|---|
| 1 | このデータを最初に作るのは誰か | イベント＝立案者（会員）。店＝会員（最初のレビューのとき。Google の結果から転記して確定）。会社の座標・bot の設定＝**運営者** ← ここで運営者が出た |
| 2 | 日常的に変更するのは誰か | 会員（参加を押す・取り消す・レビューを書く・店名を直す） |
| 3 | 止める・承認する権限を持つのは誰か | 立案者（自分のイベントの取り消しのみ）。承認フローは無い |
| 4 | お金を受け取る／払うのは誰か | いない（決済なし。Google Places の利用料は会社が払うが業務フローに現れない） |
| 5 | 集計を見るのは誰か | いない（集計・レポートの要求なし） |
| 6 | 問い合わせを受けるのは誰か | **モデルには現れないが、人としては決めた**（オーナー部署・苦情の一次受け＝Slack チャンネル・研修後の引き継ぎ先）。機能は作らない（本人が自分のものを消せるだけ・問題時は DB 直接対応）——社内に出せば苦情は必ず人に来るので、受け手を空席にしない |
| 7 | 人ではないが動くものは何か | **バッチ**（締切で不成立・集合日時で終了）、**Slack bot**（匿名投稿）、**Google Places**（店舗検索） |

### 6 類型の確認

| 類型 | いる／いない | 理由 |
|---|---|---|
| 運営者・本部 | **いる（画面なし）** | 会社座標・bot・チャンネル設定の持ち主。設定ファイル（エンジニア作業）で済ませるため**モデルには現れない** |
| 承認者・監査 | いない | 承認フローなし。「軽さ」が価値なので作らない |
| CS・サポート | いない | 不適切対処は今回作らない。大規模化したら要る＝判断が変わる条件 |
| 経営・分析 | いない | 集計要求なし。ただし「消さない」（保存期間無期限）の判断には効いた |
| バッチ・スケジューラ | **いる** | 不成立・終了は誰の操作でもなく時間で起きる。逆引きテスト（状態を動かすのは誰か）で発見 |
| 外部サービス | **いる（2つ）** | Slack と Google Places。所持物なし。相手側 ID（channel/message・place_id）と結果をこちら側に写す |

### 所持物と採否（確定）

| アクター | 所持物 | 備考 |
|---|---|---|
| 会員（唯一の人間アクター） | アカウント / 参加（押した本人のもの）/ 自分の履歴 / 自分のレビュー | 立案者・参加者はアクターではなく**役割**（取り消しは立案者だけ、という権限差で表す） |
| （共有の場） | **イベント**＝掲示板の貼り紙 / **店**＝共有マスタ | イベントは誰の私物でもない（「立案者の私物」だと匿名要件下で「持ち主が誰にも見えない所持物」というねじれが出る）。店は誰でも登録・店名も誰でも直せる |
| 運営者 | 設定値のみ（モデル外） | — |
| バッチ / Slack / Google Places | **なし** | — |

はみ出しチェック: 「2人が対等に変更」に店が該当しかけたが、別種のアクター2人ではなく会員1種の中の共有なので分割不要。5分迷った「イベントの持ち主」は上記の掲示板方式で決着。

### 網羅スイープ（プロンプトA実行）の結果

アクター・6類型の結論は変わらず。**新発見は「Slack 投稿の記録（channel / message の ID）」**——bot が投稿した相手側 ID をイベントに写さないと、成立時に元の投稿へ結果をつなげられない（教材の `Payment.transactionId` と同型）。大規模（複数社）で増える所持物（テナント・グループ・管理者ロール・通報・登録制限）は「作らない」ではなく判断が変わる条件として保持。

## コンテキストの判断（確定）

人間のアクターが会員 1 種で「担当者」軸が無効のため、変更の理由・ライフサイクル・公開性で切った。**3 つ・common は作らない**。

| コンテキスト | 記号 / 英語名 | 変更の理由 | ライフサイクル | 公開性 |
|---|---|---|---|---|
| 会員 | `member`（Member / MemberPassword / MemberSession） | 認証方式・セキュリティ | 年単位 | 秘匿 |
| イベント | `event`（Event / EventEntry） | 誘いのルールの改善 | 数時間〜1日の**揮発** | 匿名が絡む |
| 店 | `place`（Place / PlaceReview） | Google Places 連携・レビュー拡充 | 無期限の**ストック** | 全実名・全公開 |

- 判断を支える事実: 「レビューはイベントに紐づけない」「イベントは場所を持たない」の 2 決定により、**event と place は互いを知らない**。参照は ID のみ・一方向（event → member、place → member）
- **common を作らない理由**: 入居 3 条件（業務操作で変わらない／管理者が別／参照されるだけ）を満たすデータが無い。店は会員が日々書き換える運用データ（教材の売り切れと同じ判定）。運営者の所持物を設定ファイルに逃した時点で common の中身が空。商品マスタの役割は Google Places（外部）が担う。判断が変わる条件: 設定を DB 管理（管理画面）に昇格させたとき

## 業務フローの棚卸し（現在の形に更新済み）

行頭に主語・番号なしで洗い出したもの。確定した決定（提案の自動化・場所を持たない・通知ルール・終了の見え方）を反映して保守している。清書版は [01 の業務フロー](./01_requirements.md)。

```
- [運営者]   会社の座標・Slack bot を設定する（設定ファイル。チャンネルは立案時に bot 参加チャンネルから選ぶ）

- [立案者]   ログインしてイベントを立てる（内容・集合日時・成立人数・締切(既定=集合日時)・投稿先チャンネル。場所はタイトルに書く）
- [立案者]   公開する（＝自分が参加1人目として数えられる）
- [立案者]   集合日時までイベントを取り消せる（成立前・成立後とも。終了・不成立のあとは不可）
- [立案者]   自分の参加だけを取り消せるのは成立後（募集中は不可）
- [立案者]   自分の履歴で、立てたイベント（成立・不成立・取り消し込み）を見る

- [会員]     Slack の URL かホーム画面ショートカットから開く（ログイン不要で閲覧）
- [会員]     イベント一覧を見る（集合日時の昇順。募集中は進捗 2/4、成立後は「行く人 5 人」。ログイン時は自分の参加に印）／詳細を見る
- [会員]     参加を押す（ここでログイン。未ログインで押したら戻って押し直す）／取り消す／再参加する（状態と時刻の両方で判定）
- [会員]     成立後、開示された参加者の名前（読みで五十音順）と、詳細画面に常に出ている店の提案（3件・縮小平均順）を見る
- [会員]     会社周辺の店リストを見る（Google Places 検索＋登録済みの店とレビュー）
- [会員]     店を登録する（最初のレビュー時。Google の結果から店名を転記して確定・手動も可）
- [会員]     店に星と一言のレビューを書く／自分のレビューを編集・削除する

- [システム] 参加受付のその場で人数を判定し、達したら即時に成立・開示（「まだ募集中」を条件にした更新なので成立は1回だけ）
- [システム] 締切を過ぎても未達なら、不成立にする
- [システム] 集合日時を過ぎたら、終了にする（当日中は「終了」として一覧に残り、翌日から履歴のみ）
- [システム] 期限切れのログインセッションの行を消す

- [bot]      公開時に URL をチャンネルへ投稿し、投稿の記録をイベントへ写す（立案者を出さない）
- [bot]      成立したとき、結果を流す（人数のみ）
- [bot]      取り消されたとき（成立前後を問わず）、「取り消されました」を流す（誰がは出さない）

- [Google]   店リストが開かれたら、会社座標の周辺の店を検索して返す

- [-]        誰が立てたか・押したかは成立まで見えない／立案者はずっと匿名（主語なし＝例外行き）
- [-]        現在 < 締切 ≦ 集合日時／成立人数は2〜50／公開後の編集不可（取り消して立て直す・公開前に確認画面）
- [-]        成立後に人数を下回っても成立のまま／不成立・成立前取り消しは本人の履歴のみ
- [-]        閲覧はログイン不要、書き込みはログイン必須
```

### 5軸チェックの結果（確定込み）

| 軸 | 拾ったこと → どうなったか |
|---|---|
| 数 | 成立人数の下限が未定義 → **2 人以上・上限 50（立案者込み）で確定**。2 人だと相手から立案者が確定するが許容（立案者は元から名簿にいる＝1/n の端）。同一イベントへの二重参加は不可・再参加は自由 |
| 時間 | 過去の集合日時では立てられない／公開後の編集 → **編集不可（取り消して立て直す）で確定** |
| 打ち消し | 成立後に取り消されたときの知らせ方 → **Slack にも流す**。さらに成立前の取り消しも流す（URL が生きている時間帯に人為的に消えるため。不成立は時間切れなので流さない——「人為か・時間切れか」で通知の要否が分かれた） |
| 同時 | 成立は参加受付時の即時判定。同時に来ても定員が無いので両方入れるが、**成立にする更新には「まだ募集中」を条件に付ける**ので成立と通知は1回だけ。締切とぶつかったら成立を優先 |
| ゼロ | 参加0で締切→不成立。提案0・レビュー0も問題なし |
| 否定形 | Google Places 不通時は登録済みの店とレビューだけで店リストを出す（誘いは店なしで回る） |

## 呼称と命名（確定）

- **日本語は 1 概念 1 語**: イベント（←募集。募集は募集局面しか指せない）／会員（←社員・アカウント。エンティティはログインする本人）／参加／イベントの状態／公開用ID。全用語集は [03 の用語](./03_design.md)
- **英語名は 7 軸評価で確定**: `Event` / `EventEntry` / `Member`（+Password/Session）/ `Place`（+Review）。点表・却下理由・判断が変わる条件（飲食店限定運用なら Shop が勝っていた等）は [naming.md](./naming.md)。**Member の代償＝雛形 Customer 系のリネームを実装時に払う**
- **Event の主なフィールド**: `startAt`（closeAt ≦ startAt の対比が読める）・`closeAt`・`minEntries`（capacity は最大の意味で真逆だった）。経緯は [naming.md 5節](./naming.md)

## モデルの形の検討（03 に反映済みの要点）

| 対象 | 現在の考え | 詳細 |
|---|---|---|
| 取り消しの表現 | `IS_CANCELED` 1 状態＋`confirmedAt` の有無で成立前後を読む（状態を 2 つに割ると成立の事実を 2 か所に書くことになる） | [03 論点1](./03_design.md) |
| 参加の取り消し | 物理削除。「不参加という記録自体が存在しない」原則と整合。(eventId, memberId) 一意で再参加＝再 INSERT | [03 論点2](./03_design.md) |
| 値オブジェクト | 成立人数（2以上）と星（1〜5）は素の Short＋検証。使用 1 か所で型を作っても守れる範囲が広がらない | [03 論点3](./03_design.md) |
| 店名の持ち方 | 「写し」ではなく**会員が付けた呼び名**（登録時に Google から転記→会員が確定・誰でも直せる）。閉店で place_id が無効化されても「レビューは無期限」が守れる。30日リフレッシュ案は却下 | [03 論点4](./03_design.md) |
| イベントと場所 | **場所を持たない**（placeId も自由記述も無し。タイトルに書く）。event → place の依存が消えた | [03 論点5](./03_design.md) |
| レビューの範囲 | 4 フィールドで確定。訪問日（createdAt 代用）・編集フラグ（計算できる）・店名スナップショット（参照が切れない）・論理削除（全クエリに除外条件が要る）・集計列・写真を落とした | [03 論点6](./03_design.md) |
| 保存しないもの | 進捗 2/4・本人の履歴・店の平均点・提案 3 件——すべて都度計算。イベントの種類（カテゴリ）も持たない（タイトルで十分） | [02 ふるい分け](./02_analysis.md) |
| 終了イベントの見え方 | 状態の定義（終了＝集合日時）は変えず、表示だけ「当日中は一覧に残す」。集合直後の「誰が来るんだっけ」に即応 | [01 質問リスト](./01_requirements.md) |
| 開示名簿の並び順 | 表示名の五十音順。参加順・ID と相関する並びは立案者（必ず先頭になる）を特定させるため禁止——5役レビューの red team が発見 | [01 質問リスト](./01_requirements.md) |
| Slack 投稿の失敗 | 再試行し、失敗してもイベントは公開のまま。投稿の記録が無いままの成立・取り消し通知は新規投稿で流す | [01 質問リスト](./01_requirements.md) |
| URL 直接アクセスの見え方 | 一覧と同じルールを適用。募集中・成立・終了当日は誰でも詳細まで。終了翌日以降・不成立・取り消しは一律「このイベントは終了しました」の一文だけの最小表示——タイトルも名前も、不成立か取り消しかの区別も出さない（区別を出すと「誘いが流れた」が可視化される）。詳細は資格のある人のログイン時のみ | [01 質問リスト](./01_requirements.md) |
| 認証まわりの鍵 | パスワード・セッションとも自分の管理 Id を持つ（雛形 CustomerPassword の実物がこの形で、流用資産と揃える）。パスワードの 1:1 は memberId の一意制約で守る。セッションは 1:*（複数端末の同時ログイン）。会員参照は全エンティティ memberId で統一 | [03](./03_design.md) |
| 雛形との全フィールド突き合わせ | Customer⇄Member・CustomerPassword⇄MemberPassword は一致。セッションは 3 差分: token を String→**Token 型**・expiredAt→**expiresAt**（実物＋英語文法に追従）、`state` は**持たないを維持**——雛形の IS_CLOSED は定義だけで読み書きゼロの死に列、しかも findByToken が state を見ないため「state で無効化できる」と信じると事故る罠。行削除方式なら「有効＝行が在る」の一義。代償: 流用時に列を 1 本落とす | [03](./03_design.md) |
| Member.Status | 残す（無効化の操作・画面は作らない。DB 直接対応の受け皿——state 1 行でログインを止められる） | [03 論点7](./03_design.md) |
| 名簿の並び順の実装 | `Member.nameKana`（必須・全角カタカナ）を足して読み順に並べる。照合順で近似する案・uuid 順の案は却下——前者は漢字が読み順にならず「五十音順」の記述と食い違い、後者は「誰が来るんだっけ」の確認がしづらい。正しい読みが入る保証はないと明記 | [03 Member](./03_design.md)・[naming 6](./naming.md) |
| 参加できるかの判定 | state だけでなく**現在時刻も見る**。バッチが動く前の数十秒に締切後の参加を通してしまうため。ちょうどの時刻は締まっている（バッチ側の条件と裏表で隙間も重複も出ない） | [03 またがるルール](./03_design.md) |
| 成立の一回性 | 「まだ募集中」を条件にした更新で、成功したときだけ Slack に通知。同時参加と成立後の再到達を同じ 1 手で吸収する（悲観ロックは過剰） | [03 またがるルール](./03_design.md) |
| 立案者の参加取り消し | 募集中は禁止のまま、**成立後は解禁**。禁止の理由（立案者不在のイベントが募集を続ける）が成立後には効かない。副産物として「毎朝立てる人は必ず名簿に載る」が消え、名簿を重ねて立案者を絞る観測が成立しなくなる | [01 成立のルール](./01_requirements.md) |
| 開示後の名簿からの離脱 | 名簿は都度計算（＝いま行く人）のままで、消えることは見えると明記＋押す前に伝える。成立時点で固定するとスナップショットが要る上、名簿にいる人が来ない状態が生まれる | [03 論点9](./03_design.md) |
| 進捗の見せ方 | 募集中は分数「2/4」、成立後は実数「行く人 5 人」。あと乗りの「5/4」や取り消し後の「3/4 なのに成立」は壊れて見え、成立を取り消さない要件そのものが疑われる | [01 匿名と開示](./01_requirements.md) |
| 提案 3 件の式 | 縮小平均 `(3×全店平均 + 星の合計) ÷ (3 + 件数)`。単純平均は星5が1件の店が常に1位、件数下限は新しい店を永久に締め出す（選択肢を増やしたいという要求と逆） | [03 またがるルール](./03_design.md) |
| bot 投稿の失敗 | 列を足さない（3 回で諦めてログ＋作成完了画面に1行）。投稿は通知であって業務の記録ではなく、列を足すと「バッチの仕事は 2 つ」の単純さが崩れる | [01 入口・通知](./01_requirements.md) |
| セッションの掃除 | 期限切れ行の削除をバッチの仕事に足した（テーブルの単調増加を止める）。バッチの仕事は「時間で起きる状態遷移＋掃除」になった | [02 動詞の注記](./02_analysis.md) |
| API の表現 | 2 軸に分ける。状態で変わる部分は oneOf（詳細／最小表示）、ログインで増えるのは「自分が参加しているか」の 1 項目だけ。全項目 optional は実際に起こる組み合わせがスキーマから消える | [03 API に載せるフィールド](./03_design.md) |
| 匿名の検証可能性 | 「表示しないだけ」で守ると決めた以上、載せてよいフィールドの表が無いと検証できない。レスポンスのキー集合と突き合わせるテストを書けるようにした | [03 論点10](./03_design.md) |
| 雛形の流用 | 設計上は全部このアプリのエンティティ。実装で雛形 Customer 系をリネームして流用することは 03 の実装メモ 1 行に留める | [03](./03_design.md)・[naming.md](./naming.md) |
| スナップショット | 本格的なもの（PaymentItem 型）は不要——「消さない」設計が必要性を消した（マスタは消えず、金額のような確定値も無い）。写し系は slackChannelId/slackMessageId（外部 ID）・confirmedAt（成立の瞬間）・店名の初回転記の 3 つだけ | [03](./03_design.md) |

## 工程からの学び

- **動詞の 2 分類の正体**: 「状態を変える／値を返す」は動詞の全分類ではなく、**うちのモデルに対して何をするかの分類**。モデルに向かわない動詞（設定する・検索する・投稿する）は第 3 のグループとして理由付きで残す。「投稿する」は外部送信（モデル無関係）と「写す」（イベントへの書き込み）に分解できた
- **圧縮されたレビューは章ごと落ちる**: 受け取った要約は A〜E の 24 件だったが、原文には「存在しない表（§5）」と「仕様の穴（§4）」の 2 章が含まれておらず、しかも要約側の 1 件（URL 直踏みの列挙漏れ）の解決策が落ちた章の表に依存していた。要約を受け取ったら原文の見出しを数えて突き合わせる
- **雛形の列は「使われているか」を見る**: セッションの `state` は雛形に定義があるのに読み書きする処理が 1 つも無く、しかも認証クエリが state を見ていなかった。実物に合わせる原則は「正しい方を採る」であって盲従ではない
- **一括置換は固有名詞を壊す**: 呼称統一の置換で「匿名イベント募集アプリ」→「匿名イベントイベントアプリ」事故。置換後はタイトル・固有名詞の確認を必ずやる
